## 1. Résumé de l'epic

- **Stories livrées :** 3/3 (8.1, 8.2, 8.3)
- **8.1 : Catalogue persistant et réservation par code (tenant, code)** — Réécriture majeure du flux de réservation : de LiveItem-centric à CatalogueItem-centric. 25+ fichiers, polymorphisme StockTable (raw SQL), partial unique indexes. 2 rounds de CR (10 issues dont 1 CRITIQUE). 470 tests.
- **8.2 : Alimentation catalogue (fin session + CRUD dashboard)** — Upsert catalogue immédiat en live, promotion fin de session, router tRPC CRUD, page dashboard catalogue, alimentation par WhatsApp. CR : 7 issues (H1 prix 100x, H2 intégrité données). 503 tests.
- **8.3 : Lancer le live par clic** — Session live démarrée explicitement par bouton dashboard. Suppression de getOrCreateCurrentSession du webhook. CR : 6 issues M/L. 437 tests (base avant ajouts 8.1/8.2).
- **Qualité :** 23 issues CR trouvées et corrigées sur les 3 stories. 1 CRITIQUE (schéma Prisma désynchronisé). Tests : 437 → 503 (+66), 0 régression.
- **Post-epic (jour de la rétro) :** Correction formatting XOF (inputs prix entiers, placeholder "0", inputMode numeric), amélioration sidebar (Catalogue et Sessions Live en liens directs), landing page mise à jour (messaging catalogue + live + commandes).

## 2. Ce qui a bien marché

- **Transformation fondamentale de l'app :** Passage de "live only" à plateforme de vente 24/7. Le bot répond aux codes à tout moment, pas seulement en live. Le catalogue est la seule source de vérité.
- **Pattern StockTable polymorphe :** 0 duplication de logique, backward compat totale. `reserveOneUnit`, `releaseReservation`, `confirmReservation` acceptent un paramètre `table` ("live_items" | "catalogue_items").
- **Concept `createdInLive` :** Distinction élégante entre articles éphémères (live, libèrent le code après vente) et permanents (dashboard, gardent le code).
- **Story 8.3 chirurgicale :** Simple, propre, 4 tests. Séparation claire "être en live" = action explicite du vendeur.
- **Réutilisation forte :** Flux réservation, file d'attente, TTL, outbox, event log — tout réutilisé sans duplication.
- **Process CR efficace :** 23 issues trouvées avant production, dont 1 CRITIQUE qui aurait causé un crash en prod.
- **Tests solides :** +66 tests, couverture catalogue exhaustive (expiration, promotion, null guard, race conditions).

---

## 3. Défis et apprentissages

- **Schéma Prisma désynchronisé (8.1 CRITIQUE) :** `prisma/schema.prisma` non mis à jour ; les tests passaient uniquement grâce aux mocks. Découvert en CR, pas en tests. **Leçon : les mocks totaux masquent les incohérences schéma/code.** Guard nécessaire (prisma validate ou diff).
- **Convention `amountCents` pour XOF (devise sans centimes) :** `toFixed(2)`, `placeholder="0.00"`, `inputMode="decimal"` sur une devise entière. Bug H1 en 8.2 (prix affichés 100x trop élevés). Convention `* 100` / `/ 100` cohérente en interne mais UX fausse. **A traversé 8 epics avant d'être corrigé.** Leçon : vérifier le formatting avec les yeux du marché cible.
- **23 issues CR sur 3 stories (ratio en hausse) :** Complexité 8.1 exceptionnelle, mais le schéma oublié est un oubli process.
- **Pas de photo ni variantes dans le catalogue :** `mediaStorageKey` en base, infra R2 prête (Stories 3.4/5.3), mais formulaire catalogue sans upload ni gestion tailles/couleurs.
- **`CATALOGUE_SESSION_SENTINEL` :** Workaround — stockage de catalogueItemId dans le champ `liveItemId` de Waitlist. Fonctionnel mais dette technique.
